### 监督器、信箱和成果如何配合

用户先在来源会话说明任务。普通问题直接回答。用户说“先别开始”时，插件把草稿和已给条件存下来，重开桌面后能接着用。正式开始前，插件会合并同一任务分几次提出的人数、并行和审批要求。两条互斥分支即使各有一个代理，也不能满足“两人同时核对”。

监督器根据账本变化推进可以执行的步骤，定期检查跨重启的期限和需要恢复的工作。需要人工批准时，依赖这项批准的计算会等待，另一项任务可以继续。任务或步骤遇到问题时，来源会话可以收到已完成的部分以及具体卡点。

协作信箱记录谁在本次运行中向谁发出了什么请求，以及这次请求是否仍能回应。执行代理在自己的正常执行步骤里收取消息。重复消息沿用同一回执，循环请求在写入前拒绝。正式成果另行登记，是否通过验收取决于成果和核验记录。T04、T05、T06 和 T09 分别覆盖了正常回复、数据缺口、无人回复和循环请求。

用户可以从任务详情或选中的运行详情发起停止。确认页显示将要停止的任务，后端核对任务与运行的归属。再次请求会返回当前运行状态，停止动作只执行一次。对于已经发出、实际后果还不确定的操作，监督器保留人工核验入口。

`a6101a85` 还单独打开了真实卡住的旧运行 `run_01a213a757347a52986000b97f19da67`。这项模拟任务有工具活动记录。重开来源会话后，监督器找回它，并在审批中心补出一张核验卡。测试者从任务详情打开同一张卡，选择「停止跟踪」并完成第二次确认。任务状态变为已停止，步骤保留「影响未核实」。原会话收到一条停止通知。这项验证对应旧状态恢复故障。[第 5 轮复审](../audits/S6-task-session-reliability-independent-audit-round5.md)

来源会话按实际交付的清单显示成果。T07 第一次交付的三份文本合计 7580 个字符。用户在原会话追问第三份时，系统仅读取《用户体验检查报告》，答出最后一项 UX-24「错误页的下一步」并保留 `T07-END-C`。其间没有新建运行。这里实测的是原件读取范围，供应商实际计费 Token 未单独测量。

审计者抽查了前两轮 T07 的全部六个执行会话。它们只使用了内部成果登记和协作信箱。两次来源会话追问各自只有一次原件读取，回执中都只有第三份的末尾标记。T08 的普通问答没有调用工具，前后保持同一组 7 项任务和 7 个运行。T09 的 B 曾尝试查询代理名单，离线策略当场拒绝；后续协作和交付均通过内部工具完成。
