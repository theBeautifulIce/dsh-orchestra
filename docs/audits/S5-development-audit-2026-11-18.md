## 发现与处理

| 编号 | 原级别 | 基线触发与影响 | 本轮处理及证据 |
| --- | --- | --- | --- |
| S5-R1 | P1 | `resolveEffect` 接受格式正确的 `no_tool_started` 和 `stopped_confirmed`。即便当前 attempt 已有工具启动事件，仍可写入不可改的结算行，使条目从待核实消失。 | N1 检查节点事件链、实际工具记录和记忆写入领取事实。正在停止的节点不能仅凭尚未观察到启动就结算。没有可信停止确认时拒绝该分支。新增当前 attempt 已启动、停止确认不存在的负例。 |
| S5-R2 | P1 | `applyGovernedMemoryBatch` 只检查快照字段存在就调用写入端。正文或元数据与审批快照不符时，仍可能调用写入端。运行驱动虽尚无生产接线，集成调用链已经可触达该分支。 | 在同一事务核对批准决定、节点与批次、有效期、提议哈希、批准条目集合和逐条哈希，再 CAS 领取批次。回归测试篡改批准后的标题并断言写端从未被调用。 |
| S5-R3 | P1 | 写入端在提交后丢回执或只返回部分结果时，原路径分别把整批标为失败或写完，还可能把剩余批准条目标为跳过。账本无法区分真实提交结果。 | 只有明确的整批未写回执能收为失败。异常或不完整回执使批次保持 `applying`，节点进入 `indeterminate_side_effect`，运行暂停，重复推进不再调用写端。仅有本地投影时拒绝出具对账证据。回归覆盖丢回执与不完整回执。权威对账及人工恢复仍是 G5 阻断项。 |
| S5-R4 | P2 | 面板调用 `decision.acknowledge` 会返回 404。决定收口忽略面板发送的 `operation_id`，请求成功但响应丢失时查不到回执。记忆批次列表也缺生产路由。 | 补真实 HTTP 路由，确认只做 pending 到 acknowledged。带 operation_id 的决定命令在业务事务内写回执。保留既有无 operation_id 的决定收口调用。生产 HTTP 用例覆盖记忆列表、两个命令的回执与同请求重放。 |
| S5-R5 | P2 | 任务和待核实清单把裸 `side_effect_verified_none` 位当成核实事实。子流程聚合忽略结算行。完整记忆写入回执也被误计为未核实。 | 任务、清单、子流程和运行收口使用共同判据，保留不可逆策略并识别已确认的写入。子流程测试验证既往终态保持原值，父运行按当前结算事实收口。 |
| S5-R6 | P2 | G5 证据生成器仅看退出码。Q-27 之类在资源争用时跳过的用例可能以退出码 0 生成通过证据。 | Vitest 证明命令必须报告至少一项通过。新增全跳过与有执行通过两类测试。 |
| S5-R7 | P2 | Chrome 创建 DevTools 端口文件时，Windows 偶发文件锁。首次重测在 1366×900 读取文件时报 EBUSY。 | 每次视觉检查使用独立临时目录，端口文件尚未可读时在原超时时限内重试。两个视口重测通过。 |
