### P1-01 已确认的任务可能因为流程后续停用而无法继续自动派发

- **触发条件**：任务已确认并建 Run（固定了流程版本）→ 流程在执行期间被停用 → 下一轮派发仍按「已发布且启用」查询流程 → 查不到 → 抛 `CONFIRMATION_MISMATCH` → 派发泵只记日志 → 排队节点永远不再推进，任务停在 running。
- **根因**：新根运行的准入检查与已启动运行的后续派发混用了同一条查询（要求 `status='active' AND scope='reusable' AND published_by IS NOT NULL`）。
- **修复**（`src/service/task-planning.ts`）：
  - 新增 `PINNED_VERSION_SELECT`（:98-99）：按固定 workflow_id + version 取已发布版本，**不带 status / scope / published_by 过滤**。
  - `confirm()`（:283-313）新增根准入检查：流程当前不是 `active` 时抛 `FORBIDDEN`「Workflow 已停用，无法启动新任务」——这是「新根准入」。
  - `resolveApprovedPlanNodeSpecs()`（:330-364）改为只校验**已固定版本 + 内容哈希**：哈希不符才抛 `CONFIRMATION_MISMATCH`「已批准计划的固定流程版本已不可用」；工具权限被撤销时先算 `toolViolations()`（:125-145），有违规抛 `TOOL_NOT_ALLOWED`「运行期工具权限已被撤销，无法继续派发」并附 `violations`，不再伪装成版本不匹配。
  - `readChoiceSafe`（:116-122）把 `NOT_FOUND` 归一为 null，避免读到不存在的版本时抛出未归一的错误。
- **语义结果**：停用流程只挡新根运行，已启动的运行继续按自己固定的版本推进；工具撤权表现为独立的运行期权限阻断。
- **回归测试**：`tests/integration/task-plan-dispatch-after-disable.spec.ts`（本轮新建）。

### P1-02 记忆运行时的异步工作与租约时间存在冲突

- **触发条件**：一次记忆推进里某个节点的异步动作（准备记忆 / 模型评估 / 写插件）耗时超过租约期限，或宿主事件循环短暂卡顿。
- **根因**：`advanceMemoryRuntime()` 在推进开始时取一次 `now`，之后所有节点共用这个时间值；`runWorkNode()` 取了默认租约后 `await` 外部异步操作，期间不续租；操作结束后又用**操作开始前**的 `now` 去续租，于是「陈旧时刻 + TTL」等于原来的过期点，等于没续。服务端每 2 秒扫一次过期租约，于是慢操作会被误判成租约失效。
- **修复**：
  - `src/service/commands/memory-runtime.ts`：新增导出 `DEFAULT_MEMORY_LEASE_TTL_MS = 30_000`（:85，对齐执行器口径 `src/executor/run-node.ts:48`）、`DEFAULT_MEMORY_LEASE_RENEW_INTERVAL_MS = 10_000`（:87）、`DEFAULT_MEMORY_STEP_TIMEOUT_MS = 60_000`（:89）；`nowOf(deps, base)`（:500）让每轮续租与状态更新都取运行时真实时钟（注入 `clock` 时用 `clock.sample().wallClockMs`，否则回落到既有 `now` 参数）；续租间隔被 `renewIntervalOf()` 压到 ≤ TTL/3；`renewOwnedLease()`（:542）把续租绑定到 `node_run_id + attempt + lease_id + owner_epoch`；`recordLeaseLost()`（:525）失权即写 `lease_lost` 事件并停止推进该节点；`withStepTimeout()`（:566）给每个节点步骤设超时（超限抛 `OPERATION_TIMEOUT`「记忆节点步骤超时」）；写端调用前先过归属闸门，失权时一次都不许调写端；`failWorkNode()`（:752）把失败收口统一成「已领批次的写步骤 → `indeterminate_side_effect` + `pauseMemoryWrite` 对账，其余 → failed」。
  - `src/service/commands/lease.ts`：`renewLease()`（:106）新增可选 `attempt`/`leaseId`/`ownerEpoch` 归属校验（:122），不匹配抛 `STALE_GENERATION`；旧调用方不传参数时行为不变。
  - `src/service/memory-host.ts`：`createMemoryHost` 注入 `clock`（:43），生产路径 `src/index.ts:529` 起全程带真实时钟。
- **语义结果**：慢操作不再因为缺续租而制造写不确定性；失权执行者不能提交结果，也不能触碰写端；已领取的写入超时后仍走既有 fence-and-inspect 对账路径，不会重复写。
- **回归测试**：`tests/integration/memory-lease-renewal.spec.ts`
  - `AC1 有效续租：异步步骤耗时超过租约 TTL，按 ≤TTL/3 续租后维护扫描不把节点改成 startup_unknown`（:151）
  - `AC2 失权拒收：租约属主变了以后原执行者不能提交节点结果，也不许执行写端`（:209）
  - `AC3 超时可控：prepareItems 超时后节点不算完成，批次与条目都不落库，租约释放`（:271）
  - `AC4 写不确定不重复：写步骤超时后只调一次写端，走既有不确定/对账路径，再推进也不重写`（:298）

### P1-04 普通手动任务缺少当前 Run 绑定，完成后任务状态也不更新

- **触发条件**：不带预留任务 ID 的普通手动任务 → 任务行 `current_run_id` 为 NULL → 任务列表拿不到当前 Run 的待审批数、未核实数、最后心跳与运行状态；且 Run 已经 succeeded/failed，任务行仍停在 running，看板分栏与注意力排序全错。
- **根因**：`createRunInTx()` 三种任务来源里只有触发路径与预留任务路径写 `current_run_id`，普通新任务的 `INSERT tasks` 没写这一列；而 `closeRun()` 的任务状态更新还带了 `EXISTS (SELECT 1 FROM task_triggers)` 谓词，没有触发规则的任务永远不会被收口。
- **修复**：
  - `src/service/runs.ts:216`：普通新任务的 `INSERT INTO tasks (...)` 增加 `current_run_id`，值取本事务即将创建的根 run（与 run/node_run 同事务）。
  - `src/service/commands/run-close.ts:80`：任务状态更新去掉 `EXISTS (task_triggers)` 谓词，保留 `WHERE current_run_id = ?` 作为「这仍是该任务的当前 Run」的绑定态守卫——旧 Run 迟到收口不会覆盖后启动的 Run。
  - `src/infra/sqlite/migrations/043_task_current_run_binding.sql`：新增 `task_run_binding_review` 表并做**有界**历史修复——只处理 `current_run_id IS NULL` 的任务；能唯一确定所属根 Run 的补绑定并同步终态；多根 Run 或找不到根 Run 的写核对记录（`reason IN ('multiple_root_runs','no_root_run')`），不猜「最新一条」；迁移可重复执行。

## 四、验收口径与完成定义

本轮对每条 P1 都先写死「修好之后什么必须成立」，再据此设计回归用例；验收以这些不变量为准，而不是以「代码改了」为准。

### P1-01 派发与准入分离

- 新根运行只在 `workflows.status = 'active'` 时被允许，错误与「版本不匹配」分得开。
- 已启动的运行只认它自己固定的 `workflow_id + version` 与 `content_hash`；流程被停用、或后来发布了新版本，都不改变它的派发内容。
- 运行期工具撤权是独立错误码 `TOOL_NOT_ALLOWED`，且用户可见：排队节点写 `dispatch.failed` 事件、运行转 failed、任务进入待处理车道——不允许出现「只记日志、节点永远排队」的静默卡死。

### P1-02 记忆租约与真实时间

- 节点推进使用运行时真实时钟（每轮取一次 `now`），续租按真实时间发起且间隔不超过 TTL/3。
- 续租与提交都绑定 `node_run_id + attempt + lease_id + owner_epoch`；失权即中止推进并拒收迟到回执。
- 无外部副作用的步骤有显式超时；写端最多被调用一次，超时走既有「不确定 + 对账」路径，再推进不重写。

### P1-03 任务专属流程的根入口与生成

- 三种入口语义分离：普通入口起 `task_local` 必须被拒；服务端可信入口只能起「owner 绑定、版本已发布、任务未消费」的那一个 `task_local`；客户端自报 `task_id` 不构成凭据。
- 任务消费与 Run 创建在同一事务内完成，且重复启动不重复消费任务、不重复建 Run。
- 候选检索改为「先检索大池 → 按任务适配性确定性打分排序 → 最后截断」，并列时按 `workflow_id` 稳定排序。
- `task_local` 不出现在 reusable 候选目录里。

### P1-04 任务与根 Run 的绑定

- 任务与根 Run 在同一事务内建立绑定（`current_run_id`）。
- 收口只按 `current_run_id` 绑定态更新任务状态：旧 Run 迟到收口不能覆盖后启动 Run 的结果。
- 历史数据只做**有界**修复（只动 `current_run_id IS NULL`），不猜「最新一条 Run」。

### P1-05 交付验收与执行生命周期分离

- Run 的终态枚举不变；验收结论落在独立表与独立状态里，不回灌 Run 终态。
- 每条验收结论可追溯到「具体 Run + 具体交付项 + 验收规则版本」。
- Task 的「目标已交付」判定要求必需交付项全部 `passed`；证据不足记 `unverifiable`，不得记 `failed`，也不得记 `passed`。
- 后续补证重验只更新验收结论，不修改原始执行事实。

### P1-06 触发成功 ≠ 运行成功

- 就绪态四值可查：`configured` / `fired` / `executor_not_ready` / `dispatched`。
- 解析器缺失、解析不出规格、解析超时，原因都落库，不被静默吞掉。
- 触发创建 Run、写触发记录、写就绪态在同一事务内完成。
