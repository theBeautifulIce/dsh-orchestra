## 结论

G2 通过。单 agent 节点从 queued 到终态走的是生产装配：HTTP 入口 `POST /v1/workflows/load` → `POST /v1/runs` 建 run 与节点 → `POST /v1/runs/dispatch` 派发器拾起节点调 `runNode` → 收口走 `applyReport` 六步。ev-g2-01 就是从这条链路跑出来的账本片段与对账查询，不是测试里拼出来的假路径；重复上报只落一次，迟到上报被租约拦住，取消不产生新 attempt 也不改已完节点，终态必须有强证据，卡住必须挂凭据（verify_human），S2 加载 parallel 被应用层拒。G-03 / G-04 / G-05 / G-07 四条注入各自留下注入参数、前后账本片段与恢复后对账查询，证据可由 `scripts/fault-inject.ts` 重跑出同样的字节。

这一版是第一轮审计整改后重签的：第一轮独立审计给出的七条致命（生产路径缺失、门哈希失真、注入证据两段相同、重放不验链、围栏期间仍收 done、桥二次 spill 丢事件、终态可被取消改写）逐条改完并各配回归用例，见 `docs/audits/S2-independent-audit.md` 与本表证据。

第二轮独立审计（`docs/audits/S2-independent-audit-round2.md`）判 G2 不通过，列出旧七条的处置结论与十一条新缺陷；这版按它的四条 P0 与七条 P1 逐条整改：生产装配补齐（runs / dispatcher / 两条新路由）、阻塞凭据强制（裸卡住按 decision_required 拒收，节点不动）、多工具证据按工具留痕、围栏立着时取消不改状态、跨节点重放与 attempt 不符一律结构错拒、重复上报事件只留一条、门候选含删除且只认 HEAD 字节。逐条对应表见 `docs/audits/S2-round2-response.md`；其中 F-06（桥 spill 未接生产路径）与 §七.5（applyReport 的 policy 参数）未闭合，留给 S3。

第五轮独立审计（`docs/audits/S2-independent-audit-round5.md`）判 G2 不通过：致命一条是门记录拿结论为 fail 的第四轮报告签 pass，门检查只验文件名轮次、不读报告结论（P0-1）；重大三条是同一工作流版本可被 reload 改写、在飞 run 的判定条件跟着变（P1-1），工具策略仍由调用方请求体自带、模板里的 node.tools 是死字段（P1-2），createOrchestra 仍能绕过单写者锁与 epoch（P1-3）；不阻断四条是 M4 长动作缺回归与续租失败误标、门检查证据可换绑、ev-g2-10 实体 ID 对调、服务端时间基准不统一。这一版逐条整改：门检查读审计报告结论，报告结论与门记录不一致即拒绝（P0-1，回归在 tests/gate-check.spec.ts）；同一工作流版本内容不同即拒绝并抛 WORKFLOW_VERSION_IMMUTABLE（P1-1）；工具授权只认 workflow 定义，runNode 按 node_run → runs.workflow_version 取 node.tools，请求体不再收 policy（P1-2，ev-g2-12）；createOrchestra 只接受 openServiceOrchestra 下发的锁凭证，第二写者 ELOCKED、旧 epoch 写 STALE_GENERATION（P1-3，ev-g2-13）；动作总时限默认 120 秒，execution.action_timeout_ms 的配置接线留 S3（本轮只有默认值生效）；心跳续租失败落 lease_lost 事件并按租约丢失收口，长动作靠 500 毫秒续租不被 2 秒租约误判（P2-1，ev-g2-14）；ev-g2-10 的实体映射改为全篇共用一套（P2-3）。新增 G2-12 / G2-13 / G2-14 三项必过项与三份证据；原 15 项的字节复核不变，ev-g2-10 因修正实体映射重生成。见 `docs/audits/S2-round5-response.md`。

第三轮独立审计（`docs/audits/S2-independent-audit-round3.md`）仍判 G2 不通过：三条致命是工具失败还能落完成（R3-01）、判定时限拿墙钟比（R3-02）、报告入口只认弱证据（R3-03）。这一版把三条致命补成系统级判定：工具 exitCode 非零就由系统判失败并把节点卡在 blocked_post（ev-g2-08），判定时限只读 boot_id 与单调纳秒，墙钟只作展示（ev-g2-09），报告入口在收口前跑系统级证据门，弱来源、伪造痕迹、空证据一律拒（ev-g2-10）。门记录本身也按审计 R3-05…R3-09 加固：产出者必须是 human、必过项与证据是固定映射、正文两张表与 artifact 同源、正文自锚 body_hash、前序门哈希链、审计轮次锚、门记录必须先提交再校验、候选清单含批内新增又删除的文件。逐条对应表见 `docs/audits/S2-round3-response.md`；其中 BRIDGE_ACK_LAG 在 S2 生产路径不可复现，仍按例外登记，留 S3。审计另指出重复上报的事件可被重试刷膨胀（R3-04）：现在同一 report_id 的同类事件只留一条（ev-g2-11，新增必过项 G2-11）；G2-02 / G2-03 / G2-04 三条旧证据也改由 HTTP 真实入口重跑重生成（ev-g2-02 / ev-g2-03 / ev-g2-04），重跑字节不变。

第六轮独立审计（`docs/audits/S2-independent-audit-round6.md`）仍判 G2 不通过：致命两条是门记录把结论为 fail 的报告读成 pass（只取全文第一个“结论”，不锚行首），以及 G2 记录没按 18 项重签、四个哈希与自锚仍是旧的 15 项值；重大一条是工作流定义只存在内存里，服务重启后同版本可以被换一套判定条件（P1-1）。这一版把审计结论解析改成逐行只认行首唯一结论（多个结论或行内引用都判不确定），把证据 id 与文件路径固定成映射表（换绑直接拒），把审计报告限定在 `docs/audits/` 且把报告字节的 sha256 写进门记录（签后改报告会被点名）；工作流定义改为落 `workflow_versions` 表、启动时 hydrate 装回，run 建时绑定 `workflow_definition_hash`，收口前比对绑定值，同一版本改写抛 `WORKFLOW_VERSION_IMMUTABLE`。新增必过项 G2-15 与证据 ev-g2-15（同一库起两次服务：重启后定义表仍只有旧定义，改写同版本 409，在飞节点仍 verifying，弱证据收口仍 `verification_too_weak`）。
