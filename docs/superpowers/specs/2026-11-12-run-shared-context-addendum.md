# 提案（附页）：工作流内部的「共享面」

- 日期：2026-11-12
- 状态：**待主人拍板**，尚未并入实施规格
- 关联：`docs/superpowers/specs/2026-11-11-workflow-orchestration-design.md`（规格 ee17d03，等主人审阅）、`docs/orchestra-design-draft.md`（设计稿 v44）、`docs/requirements.md`
- 触发：主人问「一个已在执行的工作流里面，是否有一个内部黑板，让这串工作流里的 subagent 都能知道工作的全貌？」（本轮原话）

---

## 1. 结论先说

**现在没有黑板。** 规格与设计稿全文检索「黑板 / blackboard / 共享上下文 / 全貌 / 任务板 / 子代理 / scratch」均 0 命中。

现在有的三样东西，都不是黑板：

| 层 | 是什么 | 谁能看到 |
| --- | --- | --- |
| 账本 | events / artifacts / decisions 只追加的事实账本 | 面板、核心大脑、订阅者按查询读 |
| 查询面 | 一套统一只读查询（get_run / list_nodes / get_artifact…） | 所有外部入口统一读同一套模型（R8） |
| 节点契约 | 沿边显式绑定：payload + artifact 引用 + ≤800 字摘要 | 只有被显式连线的上下游 |

关键差别：**节点之间是「沿边传数据」，不是「同时看一张桌」。** 并行分支里的两个 agent，彼此看不见对方跑到哪、产出了什么，除非编排层在边上手工连线。

## 2. 为什么「看不到全貌」是现在设计的根因

不是遗漏，是三条硬规则叠出来的：

1. **执行器隔离**：每个 node_run 新建一个 executor 子智能体，不继承主会话历史，只拿自己的输入、工具策略、输出 schema（规格 107 / 443 / 600 / 779）。
2. **节点不做跨节点业务判断**：节点只按自己的输入、输出与判定规则工作（规格 74 / R15）。
3. **上下文预算**：大脑看到的是摘要与索引，不是执行器全文；细节按 evidence_id 去取（规格 603 / 814–820）。

这三条保证了可解释性与可回放，代价就是「同一条工作流里，兄弟节点彼此失明」。

## 3. 为什么不做「真·黑板」

一个谁都能写、谁都能改的自由文本共享空间，会直接撞上四堵墙：

| 撞点 | 后果 |
| --- | --- |
| 共享空间可写 → 事实有两份 | 破坏「事件账本是唯一事实源」与「一个节点最多一个终态」（R4） |
| 自由文本被当事实引用 | 绕过证据门，模型自报算数（R6、规格 368–398） |
| 每个节点都灌黑板 | 上下文爆炸，正是 token 预算要防的事（规格 603 / 814–820） |
| 状态散落在黑板里 | 状态机失去唯一裁决点，一个节点两个终态 |

所以补齐方向不是「加一块可写板」，而是：**共享面 = 账本的只读投影 + 一类明确不算证据的有界便条。**

## 4. 方案：两层共享面

### 第一层：共享简报（只读投影，必须有）

一个 **run 级别的只读快照**，由账本现算，不是新存储实体。

**内容（全部人话、低密度）**

1. 任务目标与当前计划（≤200 字）
2. 节点清单：每个节点一行 —— 名字、类型、状态、产出摘要（≤60 字）、是否在等人拍板
3. 已有产物索引：产物名 + 一句说明 + 哈希前 8 位
4. 等人处理的事：待拍板项、待确认的副作用，一句话一条
5. 当前卡在哪、卡在谁那里

**边界**

- 体积上限默认 4 KiB；节点多于 30 个时只给 top-N，其余压成一行「还有 N 个步骤在后面」
- 派发 node_run 时随节点输入一起注入 executor 子会话，附 `as_of_seq`（明确它是那一刻的快照，不假装实时）
- 读取者：executor（只读自己那次的快照）、核心大脑（读最新）、面板（读最新）、主聊天与其子智能体（走查询）
- 写入者：没有。共享简报是账本的投影，账本仍然单写者

**新增读视图**：`RunBrief`（对应新增查询 `get_run_brief`），与现有 `get_run` 的区别是：`get_run` 给机器口径的完整摘要与 top-N，`get_run_brief` 给人话的一页看懂。

### 第二层：节点便条（有界可写，建议有）

一类**明确不算证据**的短便条，让并行分支之间能交接发现。

**字段**：`note_id`、`run_id`、`node_run_id`、`author`、`scope`（本次运行可见 / 仅下游可见 / 仅大脑可见）、`body`（≤500 字）、`created_at`、`evidence_strength` 固定为「无」。

**用途**

- 并行分支 A 跑完，给分支 B 留一句「接口实际返回 3 个字段，不是文档里的 4 个」
- 节点给后继留一句「这一步的坑在这里」
- 人给整条运行留一句话

**硬边界（这层最要紧）**

- 便条**不是证据**：不能满足任何节点的通过条件，不能当不可逆动作的通过凭据
- 便条**不能改状态**：状态只能由状态机迁移
- 便条**不跨运行**：默认只在同一次 run 内可见（对齐「不做跨工作区共享账本」）
- 便条**有配额**：每个 node_run 最多 5 条，每次运行总量上限 200 条，超出按时间淘汰并记事件
- 便条进事件链，有序号、可追溯，不搞第二份账本

**与 DSH 原生的关系**：DSH agent team 已有会话内共享任务板（`team_task_*`，带 revision CAS），能当单场会话的临时协作面；但它不跨会话、不进账本、不受证据门约束，所以编排插件自建的是「跨会话可持久、按任务号可检索、进了账本」的那一份。

### 明确不做

- 节点之间互发消息（保持「事件 + 沿边数据」单向，可解释）
- 跨运行、跨工作区的共享空间（v1 不做）
- 把便条提升为证据的任何通道

## 5. 与现有硬规则的相容性

| 规则 | 影响 |
| --- | --- |
| R4 唯一终态 | 无影响：共享简报是投影，便条不改状态 |
| R6 证据客观 | 收紧：便条证据强度固定为「无」，不新增任何模型自报通道 |
| R7 面板只读、低密度 | 增加一块「运行共享面」只读展示 |
| R8 统一查询 | 增加 `get_run_brief` 与 RunBrief 视图，仍走同一套查询模型 |
| 1.2 不做跨节点判断 | 无冲突：读共享面不等于替兄弟节点做判断，节点判定仍只用自己的输入与规则 |

## 6. 若采纳，需要改的落点

1. 规格第 8 章：新增读视图 `RunBrief` 与查询 `get_run_brief`，写清体积上限与 `as_of_seq` 语义
2. 规格第 7 章 executor 生命周期：明确派发时注入共享简报（只读、有界、快照）
3. 规格第 3 章（节点与契约）：新增便条实体与硬边界；写明便条不是证据
4. 规格 10.5 上下文预算：共享简报计入节点上下文预算（4 KiB / 节点）
5. 设计稿第五段新增一节「共享面」
6. 面板原型：运行页加一块人话版共享面（目标 / 走到哪 / 各节点一句话 / 要你做什么），保持低密度
7. 重新跑结构校验与哈希，落新提交

## 7. 面板上长什么样（人话版，低密度）

```
本次运行：把官网首页的翻译更新到英文
进度：5 / 8 步 · 卡在「文案校对」等你拍板

● 拉取旧文案      已完成   取到 42 段
● 机翻 3 段        进行中
○ 文案校对        等你拍板  「术语表」要不要按新词条统一？
● 回写网站        未开始

产物：old.json · draft.json
备注：机翻这次只回传 3 段，剩下 2 段要人工补
```

点开任一行才展开细节；默认不显示会话编号、内部序号、节点 ID 这类对主人没用的东西。

## 8. 等主人拍板的三点

1. **共享简报**：要不要做？（我建议做，这是「知道全貌」的正解，且只读、投影、4 KiB，不碰证据门）
2. **节点便条**：要不要做？做的话便条一律「不算证据」的口径主人认可吗？
3. **注入范围**：共享简报只给 executor，还是也给主聊天侧的子智能体？（我建议两边都给，executor 那份是派发时的快照，主聊天那份随时读最新）

拍板后我按第 6 节落进规格，并重跑结构校验与哈希。
