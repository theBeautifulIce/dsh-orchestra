# dsh-orchestra 产品能力差距与后续开发路线

> 状态：规划稿，供 G4 后的路线评审；不替代现有 S5 / S6 规格、阶段门或可靠性审计。
> 基准：仓库截至 2026-11-17 的代码、G1–G4 门记录、S5 计划及用户提供的产品分析。

## 1. 产品方向

dsh-orchestra 面向用户承接目标并交付可核验成果。用户不必先设计流程或挑选执行成员；系统负责理解目标、选用已发布流程或创建任务专属流程、执行、请求必要的人类决定，并交付有证据的结果。

职责边界保持清晰：

- 流程定义要做哪些步骤；
- 执行器承担某个节点作业；
- 调度器决定何时及由谁执行；
- 策略与工具边界决定执行器可以做什么；
- 账本、事件和证据记录实际发生的事；
- 面板解释进展、需要的决定和最终交付。

本路线沿用现有账本与状态机，不以新增模块数量作为目标。所有运行仍固定不可变流程版本；运行中改计划必须走显式 Replan，不能改写在途定义。

## 2. 当前基线与差距

| 能力 | 仓库现状 | 规划判断 |
| --- | --- | --- |
| 执行可靠性 | G1–G3 已有门记录；账本单写者、事件链、租约、幂等回执、恢复、决定、并行与子流程已实现。 | 作为底座继续使用；新功能沿用 CAS、追加事件和证据规则。 |
| 流程定义与版本 | G4 于 2026-11-17 通过；草稿、校验、发布、任务专属流程及运行固定版本已具备。 | 可用于自动选择流程和生成任务专属流程，不需另造版本机制。 |
| 产品面板 | `src/client/index.tsx` 目前仅导出客户端标识；交互原型在 `docs/prototype/panel-v2.html`。 | S5 的六屏与真实读模型连接仍是近期主工作。原型里的模拟聊天不能代表真实任务能力。 |
| 任务理解与规划 | 现有 start-run 接收既有任务与流程；尚无面向任意目标的理解、流程选择/生成和规划确认闭环。 | S5 后新增纵向切片，沿用任务、task_local 流程和固定版本。 |
| Agent / 执行主体 | 每个 node_run attempt 由宿主创建并管理执行会话；有桥接生命周期与事件游标。没有独立的持久 Agent 注册/团队实体。 | 先明确执行器分配契约。只有多节点复用、路由或接管成为真实需求时，再引入 Agent 注册表。 |
| 通信确认 | 桥事件有持久回执、序号补洞与 ACK 滞后保护。 | 这是桥传输交付确认，不等同于 Agent 之间的业务消息、结果接收确认或 MessageBus。避免重复建设桥层。 |
| 权限与副作用 | 节点工具 allow/deny、工具注册校验、只读工具执行、强证据及副作用等级已有实现。 | 通用工具边界已有基础；Workspace/Agent/Task/单次 grant 的统一策略治理还未形成，扩展到写工具或外部运行时前补齐。 |
| 实时观测 | S5 计划包含事件查询、SSE、Last-Event-ID、断号重同步和轮询降级；生产客户端尚未接上。 | 按 S5 计划先完成并验收，不重复规划另一套事件流。Trace 展示作为其上层读模型能力。 |
| 产物交付 | 账本已有 artifacts 元数据表；S5 计划包含 `get_artifact` 与证据查询。 | 存储和查询有基础，面向用户的交付页、版本/来源/验收状态仍需产品化。 |
| 调度与预算 | 已有节点执行并发调度及写队列边界。 | 不另起“资源调度器”大模块；先盘点现有并发控制，再补任务预算、优先级或模型路由的具体缺口。 |
| Workspace 协作 | 当前规格与实现以单工作区/宿主内运行边界为主。 | 多成员、共享流程和跨工作区权限推迟到单用户闭环稳定之后。 |

阶段状态以仓库门记录为准：目前 G1–G4 在位，G5/G6 门记录尚不存在。下一项工程阶段仍是既定 S5（面板与记忆），不是跳过它直接铺设 Agent 团队、企业工作区或全套成本系统。

## 3. 开发顺序与里程碑

### M0：完成 S5，交付真实可用的控制面

**目标：** 让用户看到的任务、运行、决定、证据和流程都来自服务读模型，并通过 G5。

**范围：** 按 `2026-11-12-dsh-orchestra-s5-panel-memory.md` 完成读模型、查询、SSE 续传、六屏、命令回执、记忆链及其门项。把原型中的模拟状态与真实状态明确区分；所有成功/完成文案必须由真实 Run、NodeRun、回执或证据支持。

**交付与退出条件：** G5 必过项全部有可复核证据；面板断线后可从游标恢复或明确显示陈旧/轮询状态；关键按钮有输入、权限、命令、回执和失败状态契约；产物查询以 artifact id 为边界，不向客户端暴露任意文件路径。

### M1：任务入口与规划纵向切片

**目标：** 用户从自然语言目标开始，得到可检查的执行计划，再进入现有可靠执行闭环。

**实现顺序：**

1. 定义 Task Brief：目标、交付物、约束、成功条件、风险和待澄清项；记录来源与修订，不让模型直接写账本状态。
2. 做流程选择：判断已发布流程是否适配，并解释选择依据；无合适流程时生成 `task_local` 草稿。
3. 展示步骤、依赖、所需工具、风险与预期产物；需要时请求用户确认或补充信息。
4. 用户确认后发布/固定流程版本并启动现有 `startRun`；任务运行记录所选版本和计划快照。
5. 运行中只能显式 Replan：创建新的计划修订/运行边界，保留旧版与旧运行证据。

**退出条件：** 至少一个端到端场景覆盖“复用已发布流程”和“生成 task_local 流程”；确认前不会启动有副作用的节点；同一请求重试不重复创建任务或运行；运行绑定的版本不可变；计划中的未确认事实不显示为已完成。

### M2：可观测执行与结果交付

**目标：** 用户能回答“谁在做什么、卡在哪里、产出了什么、凭什么可信”。

**范围：** 在 S5 的事件流和读模型上增加 Agent/节点时间线、工具调用、等待、重试、桥事件、异常和关键路径；完善 Artifact 展示，关联 artifact、版本、来源 node_run、生成执行器、证据和验收状态。区分执行结束、结果已接收、结果已验证、已交付这几个业务阶段。

**退出条件：** 任意展示状态可追溯到账本事件或查询结果；断流和重放不重复展示；产物缺证据或未验收时不会标记为已验证交付；人工接管和恢复路径可从任务详情进入。

### M3：执行器分配与协作可靠性

**目标：** 解决真实存在的执行主体路由、结果交接和失败接管问题。

**先做契约，再扩数据模型：** 定义执行器身份、能力、会话生命周期、节点分配/接管、结果投递和确认语义。保留 `workflow node` 与执行主体的分离；同一执行器可服务多个节点、节点可按策略重派，但任何重派都受 node_run attempt、租约与幂等协议约束。

若桥 ACK 已覆盖传输层，业务 ACK 只为“接收方已处理/接受交付结果”建立单独状态，不复制桥事件序号和传输回执。按需求证据决定是否增加持久 MessageBus；先避免为静态多 Agent 团队模型引入 AgentMessage、Delivery、Receipt、Ack、Retry 五套表。

**退出条件：** 能演示执行器启动、失联、重派、迟到回报拒绝、结果未确认追踪和人工接管；旧 attempt 不能覆盖新 attempt；交付确认与执行终态分别可查询。

### M4：扩展工具前补齐策略治理

**目标：** 将现有节点工具 allow/deny 和副作用防护扩成可审计、执行时强制的授权边界。

**顺序：** 先列出当前可执行工具、宿主权限能力和失败默认行为；再设计策略继承（工作区/任务/执行主体）及有期限的单次授权；最后让统一执行入口在每次调用时校验动作与资源范围，并把授权、拒绝、操作和验证证据关联进账本。

**边界：** 在没有真实写工具需求前，保持当前只读执行基线；审批记录本身不授予宿主权限。不可逆操作必须有验证、补偿或人工接管规则。

**退出条件：** 未授权默认拒绝；授权范围、过期、撤销及策略冲突有确定语义；工具执行边界而非 UI 做最终校验；拒绝和实际副作用都可审计。

### M5：预算调度与多工作区扩展

**目标：** 依据使用数据增加任务预算、模型路由和多用户边界。

先量化全局/任务并发、等待时长、模型成本和失败重试，再按最痛的瓶颈增加配额/预算。随后明确 Workspace 成员角色、资源归属、凭据边界、流程分享/复制和版本升级策略。每一项都作为独立决策，不因原型出现 Workspace 视觉元素就默认启用多租户模型。

**退出条件：** 配额在调度执行层生效；租户数据和凭据隔离有测试证据；分享、复制、升级对既有运行版本的影响明确。

## 4. 优先级决策

| 优先级 | 做什么 | 现在的落点 |
| --- | --- | --- |
| P0 | 真实任务控制面及产品状态可信度 | 完成 S5 / G5；原型模拟不得冒充真实运行 |
| P0 | 自然语言目标到固定版本运行的闭环 | G5 后做 M1，复用 task_local、版本固定、startRun |
| P1 | Trace、事件恢复体验、Artifact 交付与接管 | 先按 S5 交付基础查询/SSE，再做 M2 |
| P1 | 执行主体路由、业务交付 ACK、接管 | M3 先验证场景和协议，避免重复桥层 |
| P1（启用写工具前） | 执行时策略治理 | M4；扩展副作用能力前完成 |
| P2 | 任务预算、模型路由、多工作区与团队共享 | 有负载和用户场景后进入 M5 |

## 5. 约束与验收纪律

- 规格、GLOSSARY 和 ADR 是领域与架构口径；本路线只安排工作，不覆盖它们。
- 每个里程碑单独拆成可审查任务、依赖、迁移与失败恢复方案；不要把 M1–M5 一次性塞进 S5。
- 不重复实现已经存在的租约、CAS、幂等、桥事件 ACK、工作流版本或副作用等级。
- 不将 Agent 与 Workflow Node 合并；执行器是可替换的执行主体，节点是流程步骤。
- 不把普通用户暴露给 DAG 设计负担；高级流程画布仍是可选管理能力。
- 各阶段关账遵循仓库 `审计要求.md` 的门与独立审计流程。本文本身不是阶段关闭或门批准。

## 6. 建议的下一步

1. 以本路线和 S5 计划为输入，做一次逐条差距核对：S5 现有计划覆盖项、产品分析建议、当前生产实现分别对应到同一张清单。
2. 先执行 S5 原定任务并通过 G5；如核对发现 S5 计划与当前实现/规格不一致，先修订计划并记录依据，不在实现中临时扩范围。
3. G5 后单独写 M1 的短规格与端到端验收场景，再开始任务入口实现。
