# dsh-orchestra 产品能力差距与后续开发路线

> 状态：规划稿，供 G4 后的路线评审；不替代现有 S5 / S6 规格、阶段门或可靠性审计。
> 基准：仓库截至 2026-11-17 的代码、G1–G4 门记录、S5 计划及用户提供的产品分析。

## 1. 产品方向

dsh-orchestra 面向用户承接目标并交付可核验成果。用户不必先设计流程或挑选执行成员；系统负责理解目标、选用已发布流程或创建任务专属流程、执行、请求必要的人类决定，并交付有证据的结果。

职责边界保持清晰：

- 流程定义要做哪些步骤；
- 执行器承担某个节点作业；
- 调度器决定何时及由谁执行；
- 策略与工具边界决定执行器可以做什么；
- 账本、事件和证据记录实际发生的事；
- 面板解释进展、需要的决定和最终交付。

本路线沿用现有账本与状态机，不以新增模块数量作为目标。所有运行仍固定不可变流程版本；运行中改计划必须走显式 Replan，不能改写在途定义。

## 3. 开发顺序与里程碑

### M0：完成 S5，交付真实可用的控制面

**目标：** 让用户看到的任务、运行、决定、证据和流程都来自服务读模型，并通过 G5。

**范围：** 按 `2026-11-12-dsh-orchestra-s5-panel-memory.md` 完成读模型、查询、SSE 续传、六屏、命令回执、记忆链及其门项。把原型中的模拟状态与真实状态明确区分；所有成功/完成文案必须由真实 Run、NodeRun、回执或证据支持。协作消息系统不属于 S5；面板可沿用现有事件/任务详情结构，为后续“待核验发现”留展示扩展点，但不提前增加消息表、命令或生命周期。

**交付与退出条件：** G5 必过项全部有可复核证据；面板断线后可从游标恢复或明确显示陈旧/轮询状态；关键按钮有输入、权限、命令、回执和失败状态契约；产物查询以 artifact id 为边界，不向客户端暴露任意文件路径。

### M1：任务入口与规划纵向切片

**目标：** 用户从自然语言目标开始，得到可检查的执行计划，再进入现有可靠执行闭环。

**实现顺序：**

1. 定义 Task Brief：目标、交付物、约束、成功条件、风险和待澄清项；记录来源与修订，不让模型直接写账本状态。
2. 做流程选择：判断已发布流程是否适配，并解释选择依据；无合适流程时生成 `task_local` 草稿。
3. 对候选流程做计划质量评估。它独立于 `WorkflowDoc` 的结构与图语义校验：图合法只说明可保存/发布，不说明它能完成用户目标。至少评估目标覆盖率、交付物可验证性、工具可用性、风险与授权匹配、依赖和并行关系合理性，以及关键假设和信息缺口。
4. 展示计划、评估结论、依据和未解决问题；未达质量门时要求补充目标、调整流程或请求人工决定，不得仅因图结构合法就启动。
5. 用户确认且质量门通过后，发布/固定流程版本并启动现有 `startRun`；任务运行记录所选版本、计划快照和质量评估版本/结果。
6. 运行中只能显式 Replan：创建新的计划修订/运行边界，重新评估并保留旧版与旧运行证据。

**计划质量门：**

- 将流程结构校验与计划质量评估分成两个结果，分别展示错误和依据；不得把二者折叠成一个“有效”标记。
- 目标覆盖率需逐项映射 Task Brief 的目标/成功条件到流程节点及预期输出，未覆盖项显式列出。
- 每个交付物必须有生成节点、验收条件和可查询证据来源；缺失时不能评为可交付。
- 工具可用性须对照运行环境中的已注册工具、节点策略和权限；不能仅凭模型生成的工具名称判定可用。
- 风险评估须识别副作用、不可逆动作、外部依赖、人工决定点和失败后的接管/恢复路径。
- 依赖评估须检查前置输入是否存在、依赖方向是否合理、并行步骤是否互不冲突，以及关键路径是否能产出目标交付物。
- 评估结果需带规则/提示版本、输入计划哈希、各维度结论、未解决项和建议动作，便于复现和审计。
- 模型可以提出语义评估意见，但不能裁决确定性事实；结构、工具注册、权限、证据绑定和必须满足的覆盖规则由系统校验。

**退出条件：** 至少一个端到端场景覆盖“复用已发布流程”和“生成 task_local 流程”；包含目标未覆盖、交付物不可验证、工具不可用、风险/依赖不合理等负例，证明质量门能阻止启动并给出可操作原因；确认前不会启动有副作用的节点；同一请求重试不重复创建任务或运行；运行绑定的版本不可变；计划中的未确认事实不显示为已完成。

### M2：可观测执行与结果交付

**目标：** 用户能回答“谁在做什么、卡在哪里、产出了什么、凭什么可信”。

**范围：** 在 S5 的事件流和读模型上增加 Agent/节点时间线、工具调用、等待、重试、桥事件、异常和关键路径；完善 Artifact 展示，关联 artifact、版本、来源 node_run、生成执行器、证据和验收状态。区分执行结束、结果已接收、结果已验证、已交付这几个业务阶段。

**退出条件：** 任意展示状态可追溯到账本事件或查询结果；断流和重放不重复展示；产物缺证据或未验收时不会标记为已验证交付；人工接管和恢复路径可从任务详情进入。

### M3：跨执行主体协作与核验闭环

**目标：** 采用“主脑控制、节点协作”：分布式专业判断，集中式任务治理。执行主体能报告发现、提出协作请求，并在预授权范围内直接交换必要信息；任务分配、优先级、资源分配、取消、计划变更和最终采纳权属于主脑/编排器或其明确授权的确定性策略。沟通权不自动包含调度权。这是协作协议，不是通用 Agent 聊天，也不建立第二套隐式调度器。

**先定三个领域对象：**

- `Finding`：执行主体报告观察、影响范围、复现材料和证据引用；报告本身不改变任何任务或其他执行主体的状态。
- `CollaborationRequest`：执行主体建议由谁核验/补充什么信息、原因、范围和期限。它是请求，不等同于派发；默认须由主脑/编排器授权后才变成正式的有界工作单元。
- `CollaborationResult`：接收方独立返回的结论、证据和限制；它可供主脑决策，不自动变成被采纳的结论或对原流程的修改。

**实现前先写短规格：** 分别记录来源 task/run/node_run/执行器与目标 task/run/执行器，避免把跨任务协作压成单一 `task_id`。定义显式授权的 `collaboration_scope`（例如同一项目的一组独立审计任务）、接收目标解析、消息幂等键、关联 ID、回复关系、载荷/证据引用、保留期和查询权限。第一版不要求持久 Agent 注册表：接收方可按协作范围内已授权的角色或执行上下文解析，由编排器选择执行器；禁止全局广播。若目标不存在或不可用，消息保持可追踪并升级给主理人。

**分阶段引入动态协作：**

1. **M3a 发现汇聚与集中派发：** 节点可自主提交 Finding；编排器做去重、范围/权限/冲突检查，由主脑决定忽略、记录、请求补证或派发核验。
2. **M3b 受控请求：** 节点可自主提出 CollaborationRequest；默认由主脑授权或拒绝，再由调度器分配接收执行主体。被拒、重复、冲突、超时和不可路由都有持久状态与原因。
3. **M3c 预授权协作：** 只有在协作策略预先限定参与者/角色、问题类型、操作范围、预算、并发、期限和最大协作深度后，低风险的信息交换或核验才可免逐条主脑批准。授权跳过的是单次审批，不是任务登记、状态可见、证据留存或资源/计划治理；任务新增、取消、优先级改变和 Replan 仍归编排器。

**第一条端到端场景：独立审计交叉核验。** S2 审计执行主体发现疑似影响 G4 的问题，提交带候选 SHA、范围、复现步骤和证据引用的 Finding；它可提出由 S4 范围执行主体核验的 CollaborationRequest，但请求在默认模式下不会自行派发。主脑检查可信度、S4 当前状态、重复请求、冲突和资源后批准/拒绝；批准后调度器派发独立、有界的核验工作。S4 接受或拒绝，接受后独立复现并返回 CollaborationResult。主脑看到原始发现、授权决定、请求、核验结果和证据链后，再决定采纳、追加修复任务或显式 Replan。S2 不得改 S4 工作状态/产物；S4 的结论也不自动等于主脑采纳。测试预授权模式时，只有满足策略约束才可省去逐次审批。

**消息生命周期：** 把请求治理与接收方处理分成两段状态：请求先处于 proposed，之后由主脑/策略记为 authorized 或 denied；只有 authorized 请求能进入 queued → delivered → accepted → completed，接收方可在 delivered 后拒绝，未处理请求可 expired。送达只表示接收方可见；接受表示接收方承接核验；完成表示业务结果已持久化并关联回原发现。桥 ACK 仍只表示宿主与执行器间的传输事件已处理，不替代请求授权或业务处理状态。重投必须幂等；接收方重复收到不得重复创建核验工作；超时/不可路由需可重试或交给主理人。

**边界、全局可见性与反循环：** 仅允许同一显式协作范围内已授权的来源与目标；该范围可以跨独立 task/run，但不得默认扩展到整个工作区。请求方不能直接创建/改写接收方任务，也不能改变其执行计划。经授权的请求由编排器登记为独立、有界的核验工作单元并固定目标 task/run；不得静默向在途 DAG 插入节点，需改变计划时走显式 Replan 或新的核验 run。Finding、请求、授权决定、派发、接受/拒绝、结果、采纳/不采纳都进入可恢复的持久记录，使主脑的读模型始终能反映实际协作状态。按发现指纹与目标范围去重，并限制协作深度、转发次数、并发、预算和期限；达到任一上限即停止并升级主理人。高影响结论由主理人采纳。消息正文与账本事件遵循脱敏和证据引用规则。

**协作验收条件：** M3a/M3b 的独立审计场景覆盖发现持久化、请求授权/拒绝、授权寻址、接收方接受/拒绝、超时重投、重复投递幂等、独立复现、证据与原发现关联、主理人采纳，以及不可路由时升级；发送方不能直接改写接收方审计产物；业务状态与桥 ACK 分开查询；达到期限、深度或转发上限后协作停止并留下原因。M3c 单独设启用门：预授权策略边界、冲突与重复抑制、预算/并发上限、撤销与恢复均有证据；M3a/M3b 的集中治理闭环稳定前不启用，且不改变集中式任务治理默认值。

### M4：扩展工具前补齐策略治理

**目标：** 将现有节点工具 allow/deny 和副作用防护扩成可审计、执行时强制的授权边界。

**顺序：** 先列出当前可执行工具、宿主权限能力和失败默认行为；再设计策略继承（工作区/任务/执行主体）及有期限的单次授权；最后让统一执行入口在每次调用时校验动作与资源范围，并把授权、拒绝、操作和验证证据关联进账本。

**边界：** 在没有真实写工具需求前，保持当前只读执行基线；审批记录本身不授予宿主权限。不可逆操作必须有验证、补偿或人工接管规则。

**退出条件：** 未授权默认拒绝；授权范围、过期、撤销及策略冲突有确定语义；工具执行边界而非 UI 做最终校验；拒绝和实际副作用都可审计。

### M5：预算调度与多工作区扩展

**目标：** 依据使用数据增加任务预算、模型路由和多用户边界。

先量化全局/任务并发、等待时长、模型成本和失败重试，再按最痛的瓶颈增加配额/预算。随后明确 Workspace 成员角色、资源归属、凭据边界、流程分享/复制和版本升级策略。每一项都作为独立决策，不因原型出现 Workspace 视觉元素就默认启用多租户模型。

**退出条件：** 配额在调度执行层生效；租户数据和凭据隔离有测试证据；分享、复制、升级对既有运行版本的影响明确。

## 4. 优先级决策

| 优先级 | 做什么 | 现在的落点 |
| --- | --- | --- |
| P0 | 真实任务控制面及产品状态可信度 | 完成 S5 / G5；原型模拟不得冒充真实运行 |
| P0 | 自然语言目标到固定版本运行的闭环 | G5 后做 M1，复用 task_local、版本固定、startRun |
| P1 | Trace、事件恢复体验、Artifact 交付与接管 | 先按 S5 交付基础查询/SSE，再做 M2 |
| P1（依赖 M1） | 受治理的跨执行主体协作与动态核验 | 先交付 M3a/M3b 集中派发和授权请求，以独立审计交叉核验验收；M3c 另设启用门，不做通用聊天 |
| P1（启用写工具前） | 执行时策略治理 | M4；扩展副作用能力前完成 |
| P2 | 任务预算、模型路由、多工作区与团队共享 | 有负载和用户场景后进入 M5 |

## 5. 约束与验收纪律

- 规格、GLOSSARY 和 ADR 是领域与架构口径；本路线只安排工作，不覆盖它们。
- 每个里程碑单独拆成可审查任务、依赖、迁移与失败恢复方案；不要把 M1–M5 一次性塞进 S5。
- 协作治理默认集中：节点有发现/报告/请求权，不因能通信就获得任务创建、派发、改计划或资源分配权。
- 不重复实现已经存在的租约、CAS、幂等、桥事件 ACK、工作流版本或副作用等级。
- 不将 Agent 与 Workflow Node 合并；执行器是可替换的执行主体，节点是流程步骤。
- 不把普通用户暴露给 DAG 设计负担；高级流程画布仍是可选管理能力。
- 各阶段关账遵循仓库 `审计要求.md` 的门与独立审计流程。本文本身不是阶段关闭或门批准。
